# Phase 0 Research: Recuperação orientada à tarefa e preparação de execução

No `[NEEDS CLARIFICATION]` markers were left in the Technical Context. This document records the design decisions the current code's actual behavior forces, verified against `internal/operations`, `internal/validation`, `internal/context`, and the relevant `SKILL.md` files rather than assumed from the backlog document alone.

## Decision 1 — Three new Task-body labels: `Depends on:`, `Verify:`, `Scope:`

**Decision**: Formalize three new single-line labels inside a Task's own body, parsed the same way `Serves:` already is (`internal/validation/requirements.go:131-160`'s `servesLinePattern`/`parseTaskCoverage` pattern): `Depends on: TASK-###[, TASK-###...]` or `Depends on: none`; `Verify: <free text>`; `Scope: <free text>`. Absence of any of the three lines means "no dependencies" / "no verification method recorded" / "no scope recorded" respectively — never an error, since every Task authored before this feature exists has none of them.

**Rationale**: `kit/skills/mister-tasks/SKILL.md`'s own Procedure step 5 already tells the authoring agent to write exactly these facts per Task ("what it depends on (another Task, or 'none'); its file/component scope; and how it will be verified") — the backlog's own gap is that none of the three has an enforced literal label, so nothing machine-readable exists today. Reusing `Serves:`'s exact grammar (one line, a fixed label, comma-separated values, an explicit "none"/absence convention) keeps one consistent Task-body authoring convention instead of inventing three different ones.

**Alternatives considered**: A single structured block (e.g. YAML-like sub-frontmatter inside the Task's own body) — rejected: every other Task-body fact (`Serves:`, the completion checkbox) is a plain one-line label, and Constitution Principle IV disfavors introducing a second, heavier authoring convention when the existing one already generalizes cleanly to three more labels.

## Decision 2 — Task-dependency parsing and cycle detection live in `internal/validation`, not the new `internal/prepare` package

**Decision**: `Depends on:` parsing, a per-Spec Task-number `DependencyGraph`, and cycle/invalid-reference detection are added to `internal/validation` (new file `task_dependencies.go`), reusing the *exact same* `DependencyGraph`/`detectCycles` types `internal/validation/dependency_graph.go` already defines for Spec-level cycles (032) — those types are already domain-agnostic `map[int][]int` graphs over bare numbers, so no new cycle-detection algorithm is written; only a new graph-construction function at Task granularity within one Spec. Two new stable Finding codes surface through `internal validate`: `task_dependency_cycle` and `invalid_task_dependency` (a reference to a nonexistent Task number, or to a Task in a different Spec).

**Rationale**: Rejecting an invalid declaration and detecting a cycle are exactly the kind of "is this structurally correct" question `internal/validation` already owns for Spec-level `depends_on` (032) — putting the *validation* half of Task dependencies there keeps that responsibility in one place, and reusing the already-generic cycle algorithm means zero new graph-theory code, only new plumbing around it (Constitution Principle IV/VI).

**Alternatives considered**: Putting dependency validation inside the new `internal/prepare` package alongside the assembly logic — rejected: `prepare` would then own both "is this declaration valid" and "assemble the response," blurring two responsibilities the rest of the project keeps separate (parsing/validation vs. orchestration); it would also mean `internal validate` could never surface a Task-dependency cycle on its own, losing the exact same "catch it before you get to `prepare`" value 032 already provides for Spec cycles.

## Decision 3 — `prepare`'s context assembly is a dedicated, deterministic extraction — `Collect`'s five-type restriction is untouched

**Decision**: `internal prepare`'s own context (served requirements' own text, Plan sections associated with those same requirements, scope, verification method) is built directly from `spec.md`/`tasks.md`/`plan.md` content already available via `artifacts.ReadBody`/`ParseDocument` — it does **not** call `contextengine.Collect`, and `internal/context/collector.go`'s existing rejection of Task targets (`ArtifactType.HasEntityID()` false for Task, collector.go:27-29) is left exactly as it is.

**Rationale**: Verified that `Collect`'s five-entity-type restriction exists specifically because Task has no independent file/frontmatter of its own and isn't one of `operations.References`'s covered types (`internal/operations/references.go`'s own `referenceableTypes` map, whose comment already says Task is explicitly out of scope) — widening that contract to accommodate one new caller would ripple into wikilink/backlink/second-hop graph traversal logic that has nothing to do with what a Task actually needs (its own served requirements' text, its own scope/verify lines, and Plan sections sharing those requirements). Spec.md's own Assumptions section already anticipated this: "a preparação de uma Tarefa passa a reunir contexto especificamente para ela, e não que a Tarefa se torna um alvo genérico de toda operação de contexto existente." Building a small, purpose-specific extraction is simpler (Principle IV) and carries none of the risk of changing an already-shipped, tested contract (033's own five-type restriction).

**Alternatives considered**: Widening `ArtifactType.HasEntityID()` (or adding a Task-specific branch to `Collect`) so a Task could be a first-class `Request.Target` — rejected: this would pull in wikilink/backlink/second-hop expansion semantics designed for the five referenceable types, none of which spec.md's own FR-010 asks for (it asks specifically for requirements/scope/Plan sections, not a general relevance graph), and would risk regressing 033's already-tested `Collect` behavior for a capability this feature doesn't need.

## Decision 4 — Plan-section association is derived from shared requirement references, not a new Plan-authoring convention

**Decision**: A Plan section (from `plan.md`'s own `ParseDocument` sections) is considered "associated" with a Task when that section's own body text contains a reference to at least one Requirement number the Task serves (via its existing `Serves:` references) — either the bare `R<N>` form or the composite `SPEC-###:R#` form, matched the same way `internal/validation`'s existing Requirement-reference parsing already recognizes both forms. No new Plan-authoring field is required.

**Rationale**: Verified (research phase) that `plan.md`'s "Requirement Coverage"/"Implementation Sequence" sections are entirely unparsed prose today — no code associates a specific section with a specific Task, and nothing in `kit/templates/plan.md.tmpl` gives Plan sections their own formal Task-linking syntax. Deriving the association from requirement references the Task already declares (via `Serves:`) needs no new authoring convention, and is exactly the same reasoning `mister-tasks/SKILL.md`'s own Decision Rules already use informally ("every requirement the Plan covers must be served by at least one Task") — this feature makes that same relationship machine-readable in the other direction (Task → Plan sections mentioning what it serves).

**Alternatives considered**: Requiring the Plan to declare, per section, which Task IDs it covers (a new `Task:` label inside `plan.md`) — rejected: this asks the human author for information that doesn't exist yet at Plan-authoring time (Tasks aren't written until `/mister-tasks` runs, after `/mister-plan`), so the label would either be perpetually empty or require rewriting `plan.md` after the fact — a worse authoring burden than deriving the same answer from data that already exists (spec.md's own Assumptions section already commits to this).

## Decision 5 — `internal/prepare` is a new package, matching `internal/context`'s own precedent

**Decision**: The orchestration itself (readiness, requirement/Plan-section lookup, response assembly, auto-selection) lives in a new `internal/prepare` package, not folded into `internal/operations` or `internal/validation`.

**Rationale**: This mirrors how `internal/context` earned its own package for a comparably-sized new capability rather than being added to `internal/operations` — Constitution Principle IV's bar ("demonstrated implementation pressure, not anticipated need") is met the same way here: `prepare` genuinely combines several existing packages' outputs (`operations.ResolveTask`/`Inspect`, `validation`'s new Task-dependency data, `contextengine.Fingerprint` for per-item consistency with 033) into one new response shape no existing package currently owns.

**Alternatives considered**: Adding `Prepare` as a new function inside `internal/operations` — rejected: `internal/operations` owns deterministic entity CRUD/resolution primitives (`Resolve`, `Inspect`, `Create`, `Fingerprint`); `prepare`'s own job (combine coverage + dependency + Plan-section data into one task-execution bundle) is a materially different, higher-level responsibility, and cramming it in would blur that package's existing single reason to change (Principle VI, SRP).

## Decision 6 — Auto-selection: lowest Task number that is Ready, computed fresh every call

**Decision**: When `--task` is omitted, `prepare` selects the lowest-numbered `TASK-NNN` in the named Spec whose computed `TaskReadiness.Ready` is `true`, recomputed from the current filesystem state on every call — never cached or reused across calls (spec FR-011, FR-013).

**Rationale**: "Lowest number first" is the same deterministic, stable tie-break `internal/ids`'s own `NextID`/`ScanTasks` already use for ordering Tasks (ascending by number) — reusing the existing ordering convention rather than inventing a new one (e.g. by declared Scope, or by count of dependents) keeps the rule simple and matches how a human author already numbers Tasks sequentially in the order they expect them to be picked up.

**Alternatives considered**: Selecting by fewest remaining blockers, or by declared priority — rejected: neither concept exists anywhere in the current Task-body vocabulary, and inventing one is exactly the kind of speculative feature Constitution Principle IV warns against without a demonstrated need; spec.md's own Acceptance Scenarios only require *a* stable, deterministic order, not a specific prioritization heuristic.
